---
name: sync-skills
description: Mirrors the skills in the scheduled-tasks repo into the Notion Skills database, one way, whenever the repo has moved.
---

Keep the Notion **Skills** database matching the `~/.claude/scheduled-tasks` repo.

**One-way, always.** The repo is the source of truth. Notion is a readable, shareable mirror
that gets overwritten. **Never copy anything from Notion back into a skill file** — Notion
rewrites markdown on save (escapes `~` and `$`, turns bare domains into links, splits nested
bold+italic into link spans), so a round trip corrupts the file a little more each pass and the
damage is invisible until an agent reads a mangled rule and does the wrong thing.

Notion database: `Skills`, data source `collection://<data-source-id>`.

## Step 1 — has anything actually changed?

```
cd ~/.claude/scheduled-tasks && bun sync-skills-to-notion.ts --dry
```

That prints the current commit and every skill's line and character count. It **refuses to run
on a dirty working tree** — if it does, commit the outstanding work first with a real message,
push, and re-run.

Then query the database for each row's `Synced from commit`:

```sql
SELECT "Name", "Synced from commit", "Lines" FROM "collection://<data-source-id>"
```

**If every row already carries the current short sha, stop. Change nothing, say nothing.** Most
nights that is the answer.

## Step 2 — update only what moved

For each skill whose sha is stale (or has no row yet), run
`bun sync-skills-to-notion.ts` without `--dry` for the full JSON — `name`, `description`,
`lines`, `source`, `commit`, `lastEdit`, and `content`.

Update the row's properties: `What it does`, `Schedule`, `Status`, `Lines`, `Source`,
`Last synced` (today), `Synced from commit`.

Then rewrite the page body. Every page opens with the same provenance callout, with the sha
updated:

```
<callout icon="🔗" color="blue_bg">
**The source of truth is the repo, not this page.**
[`<name>/SKILL.md`](<source url>) · commit `<sha>`

Regenerated by the `sync-skills` task and overwritten each time — edit the file, not this page.
</callout>
```

Below it, write a **useful summary, not a paste of the file.** A 1,600-line skill is a bad
Notion page and a good GitHub file. What belongs here: what the skill is for, the shape of a
run, its section list, and the handful of things that were expensive to learn. Someone should
be able to read the page and know whether they want to open the source.

Keep each page's existing structure and rewrite it in place with `notion-update-page` — do not
create a second row for a skill that already has one.

## Step 3 — new and removed skills

A directory in the repo with a `SKILL.md` and no Notion row gets one. A row whose directory has
gone gets its `Status` set to `paused` with a note saying when it was removed — **do not delete
the row**, the history is worth keeping.

Cross-check `Schedule` and `Status` against `list_scheduled_tasks` rather than trusting the
table hardcoded in the script; if they disagree, the scheduler is right and the script's
`SCHEDULES` map needs updating in the repo.

## Notes

- **This is a quiet task.** No Telegram message, ever. Jack finds it in Notion.
- If the Notion connector is unavailable in a headless run, do nothing and leave the shas
  stale — the next run picks it up. Do not half-write a page.
